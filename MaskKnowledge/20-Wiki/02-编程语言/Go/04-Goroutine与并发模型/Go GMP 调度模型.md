> 面向 Go 后端、云计算、AI Infra 和可观测研发面试。

## 一、从并发问题理解 GMP

操作系统真正调度的是线程。如果每个并发任务都创建一个操作系统线程，当服务需要同时处理成千上万个请求时，会出现线程栈占用大、创建和销毁成本高、内核调度压力大等问题。

Go 的解决思路是：用轻量级的 goroutine 表示并发任务，再由 Go runtime 把大量 goroutine 调度到少量操作系统线程上执行。

但只有“任务”和“线程”还不够。如果所有线程都从同一个全局队列获取任务，线程越多，对全局队列的锁竞争就越严重；调度状态和运行时资源也难以高效管理。Go 因而在 G 和 M 之间引入 P，最终形成 GMP 模型。

GMP 要解决的核心问题是：

> 如何以较低的线程和调度成本，让大量 goroutine 在多个 CPU 核心上高效、均衡且持续地运行。

## 二、G、M、P：三个角色与约束关系

|角色|准确定义|核心职责|不是什么|
|---|---|---|---|
|**G（Goroutine）**|goroutine 在 Go runtime 中的表示|保存要执行的函数、栈、执行位置、状态等信息|不是操作系统线程|
|**M（Machine）**|与 Go runtime 关联的操作系统线程|真正执行 G 中的代码，由操作系统调度到 CPU 上|不是模糊的“系统资源”|
|**P（Processor）**|Go 调度器的逻辑执行资源和调度上下文|维护本地运行队列及部分调度、内存缓存等资源|不是物理 CPU，也不只是任务队列|

三者的基本约束是：

- G 只是任务和执行现场，必须由 M 执行；
    
- M 必须绑定 P，才能执行普通 Go 代码；
    
- 一个 P 同一时刻只能由一个 M 使用；
    
- 一个 M 同一时刻只能执行一个 G；
    
- M 可以先后执行不同的 G；
    
- G 暂停后再次运行时，不保证仍由原来的 M 或 P 执行。
    

可以把它们理解成：

```
G：待处理的订单
M：真正做菜的厨师
P：包含订单队列和工作资源的操作台
```

厨师 M 必须获得操作台 P，才能处理订单 G。但类比只帮助建立直觉，面试中仍应使用“goroutine、操作系统线程、调度上下文”等准确定义。

## 三、GMP 如何完成调度

### 1. 正常调度：G 怎样获得执行

执行下面的代码时：

```
go task()
```

Go runtime 会创建一个新的 G，使其成为可运行任务，并通常将它安排到当前 P 相关的可运行队列。与 P 绑定的 M 选择一个可运行 G，操作系统再把 M 调度到 CPU 上，最终由 M 执行 G 中的代码。

这个过程可以概括为：

```
创建 G → G 进入可运行队列 → M 绑定 P → M 选择并执行 G
```

G 执行结束、进入等待、主动让出或者被抢占后，M 可以选择其他可运行 G，不需要为每个 G 创建或销毁一个线程。

### 2. 可运行任务存放在哪里

调度器中的可运行 G 主要来自以下位置：

|   |   |
|---|---|
|位置|作用|
|**P 的本地运行队列**|保存与该 P 相关的可运行 G，减少多个 M 对全局队列的竞争|
|**全局运行队列**|保存未归属于某个本地队列或需要全局参与调度的 G|
|**netpoller 就绪任务**|网络事件就绪后，等待 I/O 的 G 可以重新成为可运行任务|
|**其他 P 的本地队列**|当前 P 没有工作时，可以从其他 P 获取任务以平衡负载|

P 不等于本地队列。本地运行队列只是 P 所维护的一部分调度资源。

### 3. Work stealing：P 没有任务怎么办

不同 P 的任务数量可能不均衡：某个 P 的本地队列中有很多 G，另一个 P 却没有任务。如果空闲 P 直接停止工作，就会浪费 CPU 执行能力。

Go 调度器会让空闲 P 尝试从其他来源寻找可运行任务。其中，从其他 P 的本地队列获取一部分 G 的机制称为 **work stealing（工作窃取）**。

Work stealing 解决的是负载不均问题：让空闲的执行资源主动寻找任务，而不是让所有 G 始终依赖一个全局队列。

面试时不宜把寻找任务的具体顺序描述成永远固定不变。核心结论是：调度器会综合本地队列、全局队列、netpoller 和其他 P 的任务情况寻找可运行 G。

### 4. G 发生阻塞时，GMP 如何处理

阻塞处理是 GMP 的重点。判断调度行为时，不能只看“G 是否在等待”，而要看：

> 操作系统线程 M 本身有没有被阻塞。

#### Runtime 管理的阻塞：通常只挂起 G

典型场景包括：

- Channel 暂时无法发送或接收；
    
- 等待 Go 同步原语；
    
- 等待定时器等 runtime 能够管理的事件。
    

以 Channel 接收为例：

```
value := <-ch
```

如果 Channel 没有数据，runtime 会保存 G1 的执行现场，将 G1 置为等待状态，并把它加入对应的等待队列。M1 本身没有被操作系统内核阻塞，因此 M1 与 P1 通常仍然可用，可以继续执行其他 G。

```
阻塞前：M1 + P1 → G1

G1 等待 Channel 后：
G1 → 等待状态
M1 + P1 → 执行 G2
```

当 Channel 条件满足后，G1 会重新变为可运行状态，等待调度器安排执行。它不保证立即执行，也不保证回到原来的 M1 或 P1。

这里的核心是：

> Runtime 主动暂停的是 G，而不是让操作系统阻塞 M，所以通常不需要转移 P。

#### 网络 I/O 等待：通常由 netpoller 挂起 G

网络服务中的连接大部分时间可能都在等待数据。如果每个等待网络数据的 G 都长期占用一个阻塞线程，就无法低成本支持大量连接。

Go runtime 通常借助 netpoller 管理网络事件。数据尚未就绪时，相关 G 被挂起，M 可以继续执行其他 G；网络事件就绪后，netpoller 使原 G 重新具备运行条件，调度器再把它安排到可运行任务中。

```
G 发起网络 I/O
        ↓
数据未就绪，G 被挂起；M 继续执行其他 G
        ↓
netpoller 检测到事件就绪
        ↓
G 重新变为可运行状态
```

因此，netpoller 管理的网络 I/O 在调度效果上更接近“只挂起 G”，通常不会让一个连接长期占用一个 M。

#### 阻塞式系统调用：M 被内核阻塞，需要转移 P

如果 G1 发起一个长时间阻塞的系统调用，执行 G1 的 M1 可能进入内核并被操作系统阻塞。此时 M1 无法切换去执行 G2。

如果 P1 一直绑定在 M1 上，P1 队列中的其他 G 也无法运行。Go runtime 因此可以将 P1 与 M1 分离，再把 P1 交给另一个可用的 M2。

```
系统调用前：
M1 + P1 → G1

M1 陷入阻塞式系统调用后：
M1 + G1 → 阻塞在内核
M2 + P1 → 执行 G2、G3……
```

这里不是简单地“挂起 G1 后让 M1 执行其他任务”，因为 M1 这个操作系统线程本身已经被内核阻塞，暂时无法执行任何 Go 代码。

系统调用返回后，M1 会尝试重新获得一个 P：

- 如果成功获得 P，M1 可以继续执行 G1；
    
- 如果暂时没有空闲 P，G1 会变为可运行状态并等待后续调度，M1 可能进入空闲状态。
    

所以，不能绝对地说“系统调用返回后，G 一定先放回 P 的队列”。M 返回后也可能获得 P 并继续执行。

#### 三类阻塞的统一对比

|   |   |   |   |   |
|---|---|---|---|---|
|场景|主要等待对象|M 是否被阻塞|P 的处理|恢复方式|
|Channel、同步原语等 runtime 管理的等待|G|通常没有|M 与 P 继续调度其他 G|条件满足后 G 重新变为可运行|
|netpoller 管理的网络 I/O|G|通常没有长期阻塞|M 与 P 继续调度其他 G|网络事件就绪后 G 重新变为可运行|
|阻塞式系统调用|G 和 M|是|P 与原 M 分离，交给其他 M|M 返回后尝试获得 P，否则 G 等待重新调度|

需要避免把前两类简单称为“非系统阻塞”，因为网络 I/O 最终也依赖操作系统能力。面试中更准确的区分方式是：

- **Runtime 能否挂起 G、释放 M**；
    
- **M 是否实际陷入了阻塞式系统调用**。
    

### 5. 抢占与 sysmon：G 长时间运行怎么办

阻塞会让 G 主动失去继续运行的条件，但还有一种情况：某个 G 持续进行计算，没有主动阻塞或让出。如果它长期占用 M 和 P，其他 G 可能迟迟得不到执行。

Go runtime 支持抢占调度，可以让长时间运行的 G 暂停，使其他 G 获得执行机会。`sysmon` 是不依赖普通 P 执行循环的运行时监控线程，参与系统调用监控、抢占、定时器和 netpoll 等运行时工作。

常见的调度切换原因包括：

- G 执行结束；
    
- Channel、同步原语或定时器等待；
    
- 网络 I/O 等待；
    
- 阻塞式系统调用；
    
- 主动调用 `runtime.Gosched()`；
    
- G 被 runtime 抢占。
    

## 四、G、M、P 的数量与并行度

并发表示多个任务在一段时间内都能取得进展；并行表示多个任务在同一时刻真正执行。

对于普通 Go 代码，每个正在执行 G 的 M 都必须绑定一个 P，因此在给定时刻：

```
最大并行执行数 ≤ min(可用 M 数量, P 数量, CPU 实际执行能力)
```

`GOMAXPROCS` 控制 P 的数量，默认值通常与运行环境可用的逻辑 CPU 数量有关。它限制的是同时执行普通 Go 代码的最大并行度，而不是程序允许创建的 goroutine 数量。

### 10000 个 G、8 个 P、12 个 M

同一时刻通常最多有 8 个 G 执行普通 Go 代码。因为只有 8 个 P，最多只有 8 个 M 能同时绑定 P。

```
min(8 个 P, 12 个 M) = 8
```

原因不是“P 的队列容量有限”，而是执行普通 Go 代码的 M 必须独占一个 P。

### 1000 个 G、12 个 P、当前只有 8 个 M

如果严格假设只有 8 个可用 M，且 runtime 不再创建或唤醒更多 M，那么同一时刻最多运行 8 个 G：

```
min(12 个 P, 8 个 M) = 8
```

此时会有部分 P 暂时没有 M 绑定。但实际运行中，runtime 可能按需创建或唤醒更多 M；如果之后有至少 12 个可用 M，并且 CPU 条件允许，并行度可以继续增加，但不会超过 12 个 P 所允许的上限。

这说明三个数量分别代表不同含义：

- G 的数量表示并发任务数量；
    
- M 的数量表示当前操作系统线程数量；
    
- P 的数量表示允许同时执行普通 Go 代码的调度资源数量。
    

## 五、面试回答与易错表达

### 推荐回答

> Go 的 GMP 模型用于把大量 goroutine 调度到少量操作系统线程上执行。G 表示 goroutine，也就是任务及其执行现场；M 表示操作系统线程，真正负责执行代码；P 表示调度器的逻辑执行资源和上下文，内部维护本地运行队列等资源。M 必须绑定 P 才能执行普通 Go 代码。
> 
> 创建 goroutine 后，G 通常会被安排到当前 P 相关的可运行队列，由绑定 P 的 M 选择并执行。如果 P 没有任务，调度器还可以从全局队列、netpoller 或其他 P 获取可运行 G，其中从其他 P 获取任务称为 work stealing。
> 
> 当 G 因 Channel 等 runtime 管理的条件等待时，通常只挂起 G，M 与 P 可以继续执行其他任务；网络 I/O 通常通过 netpoller 达到类似效果。如果 M 陷入阻塞式系统调用，runtime 会将 P 与该 M 分离并交给其他 M，避免其他 G 一起等待。`GOMAXPROCS` 控制 P 的数量，并限制普通 Go 代码的最大并行度。

### 易错表达

|   |   |
|---|---|
|不准确的说法|准确表达|
|G 是“Go 协程任务”|G 是 goroutine 在 runtime 中的表示，保存任务和执行现场|
|M 是“系统资源”|M 是操作系统线程，真正负责执行代码|
|P 就是“任务队列”|P 是逻辑执行资源和调度上下文，本地队列只是其中一部分|
|P 的队列容量限制并行度|M 必须绑定 P；P 的数量限制普通 Go 代码的最大并行度|
|G 阻塞后，M 都能执行其他 G|只有 M 没被阻塞时才可以；阻塞式系统调用可能同时阻塞 M|
|系统调用返回后，G 一定进入队列|M 会先尝试获得 P；失败时 G 才等待重新调度|
|G 唤醒后会回到原来的 M 和 P|不保证，由调度器根据当时状态安排|

GMP 最终应该理解为一套协作机制：

> G 描述任务，P 提供调度资源并组织可运行任务，M 真正执行任务。大量 G 通过 P 被调度到少量 M 上；当 G 等待时，runtime 尽量释放 M 去执行其他 G；当 M 被内核阻塞时，则转移 P，保证其他任务继续运行。
